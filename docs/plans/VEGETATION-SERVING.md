# Vegetation serving path — design

Status: **design only, nothing implemented**. Answers the brief in
`TASK: design the serving path for ~15.3 MB of authored vegetation GLB`.

Constraints this design must hold, unconditionally:

- Localhost-only. Nothing here may assume, or degrade gracefully toward, a production path.
- `public/` stays exactly as small as it is today for this pack — zero bytes of vegetation GLB in
  `public/`, ever, while the founder's localhost-only decision stands.
- The pack is original authored work, not BSG game data, and the design must not blur that
  distinction with the genuinely game-derived Customs terrain package.

---

## 1. Where the pack lives

**Answer: leave it exactly where it already is — `.local-candidates/vegetation-full/`. Do not move
it under `.local-game-derived/`, and do not invent a third gitignored root.**

### The pack is not game-derived, and `.local-game-derived/` says so about itself

`scripts/lib/local-game-derived-dev.mjs`'s own header calls its directory home to "user-owned,
**game-derived** Customs truth," and `verify-build-boundary.mjs` exists specifically to prove that
no byte traceable to a local EFT install — `EscapeFromTarkov_Data`, `EscapeFromTarkov.exe`,
`Battlestate Games`, `BsgLauncher`, an absolute install path — reaches `dist/`. That whole
apparatus (the forbidden-literal scan, the drive-root/UNC regexes) is answering one question: *did
build tooling touch something extracted from the game?* The vegetation pack answers "no" to that
question by construction and says so in its own receipt:

```
"copyrightBoundary": {
  "collisionIncluded": false,
  "coordinatesCopiedIntoIndex": false,
  "gameMeshesIncluded": false,
  "gameTexturesIncluded": false,
  "geometryApproximation": true
}
```

(`.local-candidates/vegetation-full/pack-index.receipt.json`). The generator is `Khronos glTF
Blender I/O v4.5.51` — a Blender export, not a game extraction — and `.local-candidates/README.md`
says the same thing about every package it holds: "Every GLB in here was generated by this repo's
own factory scripts... from procedural code and sanitized scalar facts — never copied, traced, or
exported from the game install... If lost, the *scripts* that produced them still exist in the
repo; only the specific rendered/measured output of a specific run would be gone."

That is a materially different risk profile from `.local-game-derived/`, whose payloads (a real
heightfield, real control-map pixels sampled from the install) cannot be regenerated by running a
script again — they can only be re-extracted from the game. Filing vegetation-full under
`.local-game-derived/` would launder that distinction: a future reader (or a future automated
policy — "nothing under `.local-game-derived/` may ever ship") would have to re-derive by hand that
this one subtree is actually fine to promote once the localhost-only decision lifts, while
everything else under that root never can be. Keeping the two roots apart keeps that future
decision cheap instead of requiring an audit.

### `.local-candidates/` is the correct, already-audited home

`.local-candidates/vegetation-full/` is not a new proposal — the pack is already sitting there,
already indexed in `.local-candidates/INDEX.json` (rescue date, per-file sha256, byte/file counts,
independently re-verified — see the TASK's "ESTABLISHED FACTS"), already described in
`.local-candidates/README.md` under its own heading, already git-ignored
(`.local-candidates/` in `.gitignore`), and already carries the exact right one-line status: **"Not
wired into the renderer."** Every other package under that root (`fortress` before its promotion,
`crackhouse-final4`, `industrial-props-freeze`, `tree02-alpha-proof`, `pine-alpha-proof-final`,
`tanker-cap-probe3`) is the same kind of thing: an original-authored, factory-produced, disposable
proof output, sitting inside its own top-level review gate with its own promotion checklist
(`docs/CONTINUATION-HANDOFF-2026-08-31.md`). Moving vegetation-full out of that family into a
directory built around a different (game-extraction) threat model would be the odd choice, not the
safe one — it would need a new justification, and there isn't one here.

### A third root would be strictly worse

A brand-new gitignored root (e.g. `.local-vegetation/`) buys nothing `.local-candidates/` doesn't
already give: it is already gitignored, already gets no build-time attention, and already has a
naming/README convention an implementer can extend. A new root would just be one more line in
`.gitignore`, one more thing `verify-build-boundary.mjs` has to know about, and one more place for
a future reader to wonder "why isn't this under `.local-candidates/` with everything else its own
README says it belongs with." Reject it.

**Conclusion:** `.local-candidates/vegetation-full/` stays the source of truth. The serving route
(§2) and the boundary verifier (§3) are both built to know about that specific subtree — not all of
`.local-candidates/` (the other five packages under it stay exactly as unreachable as they are
today; scoping the route to `vegetation-full/` only is a strictly smaller blast radius than opening
all of `.local-candidates/`).

## 2. The dev route

New file, sibling to the existing plugin: **`scripts/lib/vegetation-authored-dev.mjs`**. It is a
close structural mirror of `scripts/lib/local-game-derived-dev.mjs` — same shape, same order of
checks, same deny-by-default posture — pointed at a different root, a different fixed URL prefix,
and a different (simpler) authorization source.

### Why a second plugin file, not a generalized one

The two plugins share almost every low-level primitive (loopback checks, percent-decoding,
symlink-safe resolution, header hygiene) but differ in the one thing that matters most for
security review — *what authorizes a path* — enough that forcing them through one parameterized
function would hide that difference instead of making it inspectable. `local-game-derived-dev.mjs`
authorizes a path by walking a strict, schema-validated terrain manifest
(`validateCustomsLocalTerrainManifest`) and deriving the exact legal file set from it every
request. The vegetation route authorizes a path against `pack-index.json`'s own `authoredAssets[*]
.lods[*].file` list (§ below) — a different document, a different shape, no schema validator that
exists yet. Two small, separately readable files beat one file with a branch a reviewer has to
untangle. If a third local-serving need ever appears, that is the point to extract the truly
shared primitives (loopback/host checks, percent-decoding, symlink-safe resolve) into a common
module — not before.

### Constants

```js
export const VEGETATION_AUTHORED_DIRNAME = 'vegetation-full';
// Anchored to this file, exactly like LOCAL_GAME_DERIVED_ROOT.
export const VEGETATION_AUTHORED_ROOT =
  join(REPOSITORY_ROOT, '.local-candidates', VEGETATION_AUTHORED_DIRNAME);
// A distinct `/@…` prefix: cannot collide with a public/ asset path, and is
// visibly distinct from /@local-game-derived/ in any log or network panel.
export const VEGETATION_AUTHORED_ROUTE = '/@vegetation-authored/';
```

### Method / origin / host gate — identical to the existing plugin, verbatim policy

- `GET`/`HEAD` only; everything else → 405 with `Allow: GET, HEAD`.
- `req.socket.remoteAddress` must satisfy `isLoopbackAddress()` → else 403.
- Every `X-Forwarded-*` request header → 403 (a proxied request means the socket address is no
  longer proof of a local client).
- `Host` header must resolve (via `hostHeaderHostname()`) to a loopback hostname → else 403.
- Reuse `isLoopbackAddress`, `hostHeaderHostname`, `normalizeAddress` and `decodeSegment` by
  **importing them from `local-game-derived-dev.mjs`**, which already exports them, rather than
  copy-pasting the regexes a second time. (This is the one piece of intentional coupling between
  the two files — pure functions with zero knowledge of either root, so importing them does not
  reintroduce the "one file, two authorization stories" problem above.)

### Path shape gate — identical policy

- `MAX_PATH_LENGTH` / `MAX_SEGMENTS` same values (1024 / 32).
- Percent-decode each segment with the existing `decodeSegment()` (rejects `.`, `..`, embedded
  `/`, `\`, NUL, leading/trailing space, and undecodable escapes) — imported, not reimplemented.
- Empty segment (trailing slash, `//`) → 404, indistinguishable from "absent", exactly as today.

### Extension allowlist — what, and why exactly this and nothing else

```js
const CONTENT_TYPES = new Map([
  ['.glb', 'model/gltf-binary'],
  ['.json', 'application/json; charset=utf-8'],
]);
```

**`.glb` — required.** It is the only payload format the pack ships (93 files, confirmed: `find
.local-candidates/vegetation-full/assets -type f | sed -E 's/.*\.//' | sort | uniq -c` →
`93 glb, 93 json`, nothing else). `SAFE_ASSET_FILE` in `src/customs-authored-vegetation.js`
(`^assets\/[A-Za-z0-9_.-]+\/[A-Za-z0-9_.-]+-lod[0-2]\.glb$`) is the adapter's own contract for what
a legal asset path looks like, and every `file` value in `pack-index.json` already matches it
verbatim (e.g. `"file": "assets/birch01/birch01-lod0.glb"`) — the route's job is only to serve
exactly that same file set, nothing wider.

**`.json` — required, for exactly two files, not "any JSON."** `createCustomsAuthoredVegetationRuntime()`
takes `packIndex` as a JS value, not a URL — a future wiring pass (out of scope here) has to obtain
that object from *somewhere* at runtime, and the only localhost-safe way to do that without baking
1.85 MB into any bundle is to `fetch()` it from this route. So `pack-index.json` (1.85 MB, the
catalog the adapter normalizes) and `pack-index.receipt.json` (863 bytes, its own hash receipt —
useful for a future wiring pass to sanity-check the fetched bytes before trusting them) are the two
JSON files the route needs to serve. **`generation-manifest.json`, the 93 per-asset
`*.receipt.json` sidecars, and everything under `logs/`, `qa/`, `validation/`, `verification/` are
never served** — they exist for human/offline review, not runtime consumption, and the
manifest-driven authorization below (not the extension allowlist alone) is what keeps them
unreachable even though their extension is allowed.

**No `.ktx2`, no bare `.png`.** The measured fact that closes this question: every texture in the
pack is baked *into* its GLB by the Blender exporter (same `find | uniq -c` above — zero `.png`,
zero `.ktx2`, zero `.bin` anywhere under `assets/`). `qa/previews/*.png` and
`qa/contact-sheets/*.png` are contact-sheet renders for human review, not runtime textures, and are
excluded by the manifest-driven authorization the same way the non-served JSON is. There is nothing
for a texture extension to serve, so the allowlist does not carry one. If a future LOD or texture
pipeline ever ships *unbaked* KTX2 textures alongside the GLBs, add `.ktx2` to this map **and**
extend `collectAuthorizedVegetationPaths()` (below) to enumerate them from the manifest at the same
time — never widen the extension map alone, or every other `.ktx2`/`.png` anyone ever drops into
`vegetation-full/` (a stray screenshot, a leftover render) becomes servable too.

### Confirming this cannot widen the *existing* route

`local-game-derived-dev.mjs` and `vegetation-authored-dev.mjs` are two independent Vite middlewares
registered separately in `vite.config.js`, each closed over its own root directory and its own
fixed URL prefix (`/@local-game-derived/` vs `/@vegetation-authored/`). `CONTENT_TYPES` in the new
file is a **module-local `const`** inside `vegetation-authored-dev.mjs` — it is not exported, not
imported by, and not merged into `local-game-derived-dev.mjs`'s own `CONTENT_TYPES` map. The
existing route's `resolveLocalGameDerivedRequest()` still checks `pathname.startsWith
(LOCAL_GAME_DERIVED_ROUTE)` first and returns `{ok:false, status:null}` (delegate to `next()`) for
anything under `/@vegetation-authored/…`, exactly as it already does for every other URL shape
(proved by the existing `'delegates every request outside the fixed route'` test). Adding `.glb`
support to the new plugin cannot make `/@local-game-derived/*.glb` servable, because that plugin's
`isAuthorizedCustomsPath()` still only authorizes paths present in the Customs terrain manifest,
which never lists a `.glb` — the extension allowlist is necessary but not sufficient in *both*
plugins; manifest authorization is the actual gate in both, and the two manifests are disjoint
documents.

### Manifest-driven authorization (mirrors `isAuthorizedCustomsPath`)

```js
const PACK_INDEX_SEGMENTS = Object.freeze(['pack-index.json']);
const PACK_INDEX_RECEIPT_SEGMENTS = Object.freeze(['pack-index.receipt.json']);
const MAX_PACK_INDEX_BYTES = 4 * 1024 * 1024; // pack-index.json is measured at 1.85 MB; headroom, not a promise.

export function collectAuthorizedVegetationPaths(packIndexValue) {
  // Minimal structural check — NOT a full schema validator (none exists yet for this
  // document shape; unlike validateCustomsLocalTerrainManifest for the terrain manifest).
  // Deliberately strict about the one thing that matters for a static-file route: every
  // `file` value must already match the adapter's own SAFE_ASSET_FILE contract, so this
  // function can never be tricked into authorizing a traversal-shaped string.
  const authorized = new Set(['pack-index.json', 'pack-index.receipt.json']);
  const assets = Array.isArray(packIndexValue?.authoredAssets) ? packIndexValue.authoredAssets : [];
  for (const asset of assets) {
    for (const lodEntry of Array.isArray(asset?.lods) ? asset.lods : []) {
      const file = lodEntry?.file;
      if (typeof file === 'string' && SAFE_ASSET_FILE.test(file)) authorized.add(file);
    }
  }
  return authorized;
}

async function isAuthorizedVegetationPath(root, segments) {
  const indexFile = await resolveLocalGameDerivedFile(root, PACK_INDEX_SEGMENTS); // reused helper, imported
  if (!indexFile || indexFile.size > MAX_PACK_INDEX_BYTES) return false;
  try {
    const bytes = await readFile(indexFile.path);
    const packIndex = JSON.parse(bytes.toString('utf8'));
    return collectAuthorizedVegetationPaths(packIndex).has(segments.join('/'));
  } catch {
    return false; // an unreadable/invalid index authorizes nothing, including itself
  }
}
```

`resolveLocalGameDerivedFile()` (realpath containment + regular-file-only) is imported and reused
verbatim from `local-game-derived-dev.mjs` — it is already root-parameterized and has no knowledge
of either manifest shape, so it is exactly the kind of primitive worth sharing (§ above).

`SAFE_ASSET_FILE` is imported from `src/customs-authored-vegetation.js` (already exported? — if
not, export it; it is the adapter's own single source of truth for a legal asset path, and the dev
route re-deriving that regex independently would be exactly the kind of drift this whole design is
trying to avoid — the route must authorize precisely the same file shapes the runtime adapter will
ever ask for, no more).

### Headers, symlink handling, everything else

Identical to `local-game-derived-dev.mjs`: `no-store`, `X-Content-Type-Options: nosniff`,
`Cross-Origin-Resource-Policy: same-origin`, `Content-Length` set explicitly, HEAD returns headers
with no body, symlink escapes refused via `realpath` containment (`vegetation-full/` currently
contains no symlinks — confirmed by the directory listing — but the check costs nothing and closes
the same hole the existing route closes).

### `vite.config.js`

```js
import { vegetationAuthoredDevPlugin } from './scripts/lib/vegetation-authored-dev.mjs';
// …
plugins: [tarkovAssetCacheDevPlugin(), localGameDerivedDevPlugin(), vegetationAuthoredDevPlugin()],
```

`apply: 'serve'` only, exactly like the existing plugin — absent from `vite build` and from
`vite preview` (which serves the *production* build) by construction, not by convention.

## 3. `verify-build-boundary.mjs` additions

The existing verifier is hardwired to one local root
(`DEFAULT_LOCAL_ROOT = .local-game-derived`). It needs to know about a **second** local root it
must prove never reached `dist/`, without diluting what it already proves about the first.

### Generalize to multiple local roots (backward-compatible)

```js
export const DEFAULT_VEGETATION_ROOT =
  resolve(REPOSITORY_ROOT, '.local-candidates', 'vegetation-full');

// verifyBuildBoundary() gains `localRoots` (array), defaulting to
// [DEFAULT_LOCAL_ROOT, DEFAULT_VEGETATION_ROOT]. The existing single `localRoot` parameter
// keeps working — it is normalized to `[localRoot]` — so every current call site and every
// existing test (which passes `localRoot` singular) is unaffected.
```

`collectLocalPackageHashes(root)` stays single-root and pure (it is already correctly scoped and
tested); `verifyBuildBoundary()` calls it once per entry in `localRoots` and unions the resulting
hash → source maps. `localPackagePresent` becomes true if *any* root is present;
`localPackageHashCount` sums across roots the same way `scannedBytes` already sums across files.
The pairwise "must not contain each other" guard against `distDir` (today checked against the one
`localRoot`) runs against every entry in `localRoots`.

### Path-segment additions

```js
export const FORBIDDEN_PATH_SEGMENTS = Object.freeze([
  '.local-game-derived', 'local-game-derived', '@local-game-derived', 'local_game_derived',
  '.local-candidates', 'local-candidates', '@vegetation-authored', 'local_candidates',
  'vegetation-full', 'vegetation_full',
]);
```

`.local-candidates` / `local-candidates` / `local_candidates` mirror the existing three-spelling
pattern for the new root name. `vegetation-full` / `vegetation_full` are added one level more
specific, because `.local-candidates/` holds five *other* packages that must stay just as
unreachable as they are today — catching the package name itself, not only its parent directory
name, is a second independent tripwire if a future build step ever copies
`.local-candidates/vegetation-full/…` in without preserving the `.local-candidates` segment (e.g.
a script that copies straight from `vegetation-full/assets/`). `@vegetation-authored` (no leading
dot — this one is the *route* prefix, not a directory name) is listed for the same reason
`@local-game-derived` already is: if it ever appears as a **path segment** inside `dist/`, that can
only mean a build tool wrote a file or directory named after the dev route, which is itself
suspicious regardless of content.

Do **not** add every individual family name (`birch01`, `pine03`, …) — thirty-one near-arbitrary
english/botanical words is exactly the kind of over-fit list that produces false positives against
unrelated legitimate content later (a labels file that happens to say "birch," a place name), for
no real gain: the hash check (below) is what actually proves byte-identity regardless of what a
copied file gets renamed to, and it does not depend on guessing names.

### Content-literal addition

```js
export const FORBIDDEN_CONTENT_LITERALS = Object.freeze([
  '.local-game-derived', 'EscapeFromTarkov_Data', 'EscapeFromTarkov.exe',
  'Battlestate Games', 'BsgLauncher',
  '.local-candidates',
]);
```

Same reasoning the existing comment already states for `.local-game-derived`: this string "can
only appear if build tooling touched the local directory." `/@vegetation-authored/` is
**deliberately absent** from this list, for the identical reason `/@local-game-derived/` is absent
today — it is a loopback-gated URL constant that a future wiring pass will legitimately reference
in application source (to build the fetch URL for `pack-index.json` and each GLB), it resolves to
nothing once `vite build`/`vite preview` are serving, and flagging it would make the build fail on
its own correct dev-only code. The directory-name literal (`.local-candidates`) stays flagged; the
route-string literal does not — exactly mirroring the existing split for the terrain route.

### Manifest-hash scraping addition

```js
const HASH_MANIFEST_NAMES = Object.freeze([
  'manifest.json', 'extraction-report.json',
  'pack-index.json', 'pack-index.receipt.json',
]);
```

`pack-index.json` declares every asset's `sha256` (prefixed `sha256:…`, but `SHA256_HEX`'s `\b`
boundary matches the same either way — verified against a live value from the pack:
`"sha256:d583759de8a0c9f51069c61b0d9d606afcf0568cfb0d08bac054ce9ae71ab83a"` contains a clean
64-hex-char run immediately after the colon). `pack-index.receipt.json` additionally declares
`catalogSha256` and `generationManifestSha256`. Adding both to `HASH_MANIFEST_NAMES` means a build
artifact byte-identical to a *declared* hash is caught even in the (currently hypothetical) case
where the specific GLB file itself was later deleted from `vegetation-full/` — the same
belt-and-suspenders the terrain route already gets from `extraction-report.json`.

### File-name addition

```js
export const FORBIDDEN_FILE_NAMES = Object.freeze([
  'extraction-report.json',
  'pack-index.json', 'pack-index.receipt.json', 'generation-manifest.json',
]);
```

Any build-output file literally carrying one of these names can only exist because something
copied it out of the local package — flag unconditionally, independent of hashing.

### Why the suffix check (`FORBIDDEN_FILE_SUFFIXES`) does *not* gain `.glb`

This is the one place the two packages genuinely differ and the design must not paper over it:
`.f32le` is a suffix unique to the terrain package, so forbidding it outright is free — nothing
legitimate in `dist/` will ever end in `.f32le`. **`.glb` is not unique.** `fortress/*.glb` is
already committed under `public/assets/3d/customs/authored/fortress/` and legitimately ships to
`dist/` today. Adding `.glb` to `FORBIDDEN_FILE_SUFFIXES` would make every future production build
fail on its own admitted assets. So `.glb` protection for this pack rests on the **hash check
alone** (byte-for-byte identity, immune to renaming, immune to the file living at any path) plus
the path/name checks above (which catch the common case of a lazy `cp -r`). This asymmetry is
intentional and should be called out in the verifier's own header comment when implemented, the
same way the current header enumerates its three independent checks — so a future reader does not
"fix" the apparent gap by forbidding `.glb` wholesale and breaking `fortress`.

  regression test for the asymmetry above: it proves the verifier was never taught to blanket-flag

  boundary protection cannot silently break the already-shipping fortress assets.
- the CLI's `--dist-dir`/`--local-root` argument surface: decide alongside implementation whether
  `--local-root` becomes repeatable (`--local-root A --local-root B`) or a second named flag
  (`--vegetation-root`) is added; either way, a CLI-level test proves the flag(s) reach
  `verifyBuildBoundary()` as `localRoots`, and that omitting the new flag still defaults to
  scanning both `DEFAULT_LOCAL_ROOT` and `DEFAULT_VEGETATION_ROOT` (the common case — `npm run
  build` calls the script with no arguments today, and must keep protecting both roots without any
  `package.json` change).

## 4. First-load cost and caching strategy

**Measured input (from the TASK's established facts):** total pack ≈ 15.3 MB of GLB across 31
families × 3 LODs; a given camera position fetches somewhere between 0.6 MB (tight, near view,
mostly LOD2/LOD1 in-frustum cells) and 12.1 MB (wide view pulling many cells' LOD0) depending on
which of the 703 `128 m` cells are in range at which LOD, per `CUSTOMS_AUTHORED_VEGETATION_LOD_POLICY`
(`nearMaxM: 110, mediumMaxM: 280, hysteresisM: 20`).

### Strategy: browser HTTP cache, not `no-store` — the one deliberate divergence from the terrain route

The terrain route serves `Cache-Control: no-store` because its payload can legitimately change
between requests within one dev session (a re-run of the local extraction produces new tile bytes
at the same path) and the terrain route already gates every single terrain fetch through the
strict manifest anyway, so there is no meaningful "avoid re-fetching" win to chase there — the
terrain package is fetched roughly once per page load, not once per cell per LOD change.

The vegetation route is different in kind: `partitionCustomsAuthoredVegetationCells()` re-derives
`requiredAssetLods` on every camera-driven cell/LOD repartition (per the pack's own review note,
flagged as F3, "expensive per-camera-tick repartition" — a pre-existing adapter concern, out of
scope to fix here, but it means the *same* `assetId` × `lod` pair can legitimately be requested
again as the camera moves back and forth across a cell boundary within one session). Re-fetching
15.3 MB of static, content-addressed-by-sha256 GLBs from disk on every such boundary crossing is
pure waste on localhost — the file on disk does not change between requests in one dev session the
way a terrain re-extraction can.

So: **`vegetation-authored-dev.mjs` sends `Cache-Control: public, max-age=31536000, immutable` for
`.glb` responses only**, not `no-store`. This is safe specifically *because* the route is
manifest-authorized against `pack-index.json`'s own declared `sha256` per file — the same
content-addressing property that makes `immutable` a correct claim, not a hopeful one: if a GLB at
a given `assets/<family>/<family>-lodN.glb` path is ever regenerated with different bytes, its
`sha256` in `pack-index.json` changes too, but the **path does not** — so a stale browser cache
entry at the old path would silently serve superseded geometry with no cache-bust. **Mitigation:**
document this explicitly (in the plugin's header comment and here) as a known dev-workflow
trade-off — after regenerating the pack, a hard-reload (or DevTools "Disable cache" during active
vegetation-factory iteration) is required, exactly the same caveat any content-addressed asset
pipeline carries when the addressing lives in a side-channel manifest instead of the URL itself. A
future, sturdier option — noted here, not built now, since it is unnecessary until vegetation
regeneration inside one session is an actual workflow — is to fold the per-asset sha256 into the
served path or an `ETag`/`If-None-Match` cycle instead of relying on `max-age` alone; that is
strictly more work than a plan-doc scope needs today.

`pack-index.json` / `pack-index.receipt.json` responses **keep `Cache-Control: no-store`** (do not
extend the `immutable` treatment to them): the catalog is the one thing a future wiring pass is
likely to re-fetch deliberately after a pack regeneration specifically to pick up new declared
hashes and asset lists, and it is small (1.85 MB once, not re-fetched per cell/LOD change) enough
that caching it buys nothing worth the staleness risk.

### What this does *not* solve, and is explicitly out of scope here

Reducing draw calls (1,333–1,467 across `prototypeCells = 703`), reducing first-paint bytes below
today's 0.6–12.1 MB range, or fixing the adapter's F1 (all-or-nothing catalog completeness) / F3
(per-tick repartition cost) concerns are **runtime/adapter design questions, not serving-path
questions** — the founder's brief for *this* task is specifically "design the serving path," and
those are `src/customs-authored-vegetation.js` concerns this design pass is explicitly barred from
touching. `immutable` caching is the one lever available purely at the serving layer that measurably
helps the stated 0.6–12.1 MB "per camera move" cost without touching adapter code: a cell the
camera has already visited at a given LOD in this session becomes a cache hit, not a re-fetch,
which is the serving-layer's entire contribution to that number.
